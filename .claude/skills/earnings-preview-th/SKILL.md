# Earnings Preview (Thai, data-grounded)

Produces the kind of document built for ORCL Q1 FY2027 in this project: a single-page, Thai-language earnings ledger combining real pulled data with researched narrative context, published as an Artifact. Includes a post-earnings **review** mode and tightens two things that broke in practice historically: event-return timing and unlabeled-confidence claims in the ecosystem map.

## Before starting

Ask only if genuinely ambiguous: which ticker, whether the user wants English or Thai (default Thai unless the project/user has established otherwise), and **preview vs. review**:
- If the next report date (from `t.earnings_dates`) is in the future relative to today, default to **preview**.
- If it's in the past, default to **review** — the user almost always wants the just-reported quarter explained, not last quarter's stale preview.
- If genuinely ambiguous which fiscal quarter, ask once rather than guessing.

Everything else — which sections to include — defaults to the full structure below unless the user asks for less.

**Keep code/API detail out of reader-facing text.** `t.earnings_dates`, `yfinance`, `revenue_estimate`, and similar identifiers are internal reasoning aids — the target reader is not a programmer and doesn't know what a "DataFrame accessor" is. The subtitle/intro line should say the plain-language fact ("[บริษัท] ยังไม่ประกาศผลไตรมาสนี้ (กำหนดประกาศ [วันที่]) เอกสารนี้จึงเป็นการสรุปสิ่งที่ตลาดคาดการณ์ไว้ล่วงหน้า" for preview mode), never narrate the lookup itself. Method names belong only in the footer's source list, where a technical reader who wants to reproduce the pull can find them.

## Data pass — prefer yfinance over web search for anything numeric

Web search summaries drift: mislabeled fiscal quarters, stale consensus figures, numbers quoted out of context. Whenever a number can come from `yfinance`, pull it directly instead of trusting a web-search summary. Check `pip show yfinance` / `import yfinance` first; install if missing.

For `t = yf.Ticker(TICKER)`, pull:
- `t.earnings_dates` — next/most recent report date + timing (before/after market), and the consensus EPS for that quarter (more reliable than search-engine summaries, which repeatedly surfaced a stale/wrong EPS figure in this project).
- `t.earnings_history` — last 4 quarters: EPS estimate, actual, surprise %. Use this for the beat/miss table. In review mode, this row now includes the just-reported quarter — use it as the actual, not a second web-search figure.
- `t.info` — `revenueGrowth`, `forwardPE`, `pegRatio`, `marketCap`, `operatingMargins`, `currentPrice`, `targetMeanPrice`, and (if present) `revenue_estimate` / `earnings_estimate` for consensus revenue.
- `t.recommendations` — analyst buy/hold/sell distribution (use the most recent `period` row).
- `t.analyst_price_targets` — low/mean/median/high, compute upside from current price.
- `t.history(start=..., end=...)` — for (a) YTD price return vs 2-4 peer tickers, normalized to % change from day 1, and (b) **event-day stock reaction** around each of the last 4 earnings dates. Pull all 4 data points, don't cherry-pick one — this is often stronger evidence than a single-quarter anecdote for any claim like "this stock trades on X, not on EPS."

Pull the same `.info` fields for 2-4 sector peers to build a valuation/growth comparison table.

### Event-return timing — use the actual trading session, not a blanket "next day"

A flat "close-to-close the day after" rule breaks whenever the report lands after market close, on a weekend, or near a holiday — it silently compares the wrong two closes. Use the release timing from `t.earnings_dates` (or IR confirmation) to pick the correct pair, and label the result **"earnings-event close-to-close return"** rather than "next-day return":

| Release timing | Reference close | Event close |
|---|---|---|
| Before market opens | Previous trading session close | Release-day session close |
| After market closes | Release-day session close | Next trading session close |
| Weekend or exchange holiday | Last session close before release | First session close after release |
| Unknown timing | Don't guess a precise window | State it's unavailable, or show both candidate windows labeled as such |

`Return = 100 * (event_close / reference_close - 1)`. Use split-consistent, non-dividend-adjusted closes unless you explicitly label the series as a total-return proxy. Do this for all 4 historical events individually — don't reuse one company's session-calendar assumption for another ticker without checking its own holiday calendar.

This table is a computation aid for you, not reader-facing content — apply it silently when picking which two closes to diff, but don't render the table itself in the document. The reader needs the answer ("ราคาหุ้นเปลี่ยนไปเท่าไรวันถัดจากประกาศ"), not the reference/event-close lookup logic behind it. A one-line caption naming which two sessions were compared (e.g. "ADBE ประกาศหลังปิดตลาด จึงเทียบราคาปิดวันประกาศกับวันทำการถัดไป") is enough transparency — it does not need its own table.

## Research pass — for what yfinance can't give you

Web search for: management's own guidance from the most recent earnings call (revenue/EPS/segment growth ranges), segment revenue mix for the "company overview" section, backlog/bookings metrics if relevant to the sector, and the company's position in its industry — named upstream suppliers/financing partners and downstream customers, with tickers where public.

**Three failure modes to watch for:**
1. **Conflicting numbers under the same round figure.** A company can guide two different things (e.g. revenue guidance and capex guidance) to numbers that happen to land near each other. Never write a bare "$XXB guidance" — always name what it's guidance *for*, and if two different metrics collide on a similar number, call that out explicitly so a reader doesn't conflate them.
2. **Don't force a literal "supply chain" onto a company that doesn't have one.** A services/cloud/software company has no factory-floor supply chain. If asked for one, reframe as the real dependency chain (compute/GPU supply, data-center & power buildout, financing, customer concentration) or, better, a full ecosystem map: named upstream suppliers/financing partners → the company → named downstream customers, with public tickers shown so the reader can see which other stocks are implicated. Watch for companies that are *both* supplier and customer at once (flagged as a specific, interesting fact, not smoothed over). **Actively search for named public-company customers** (customer-story pages, case studies, award/recognition press releases, keynote logos) before settling for generic category nodes on the downstream side ("องค์กรทุกขนาด") — a category node is a fallback for when no named customer is disclosed, not the default. Every named customer that trades publicly gets its ticker shown next to it, same as an upstream supplier would.
3. **Don't present a web-search claim with the same confidence as a filing.** Tag each ecosystem-map relationship and each non-yfinance number with one of three levels, inline or in a footnote, using plain Thai words rather than a formal ledger schema:
   - **ยืนยันแล้ว** — the company's own filing, earnings call, or press release states it directly.
   - **มีรายงาน** — a credible secondary source (news outlet, analyst note) states it, but there's no primary confirmation.
   - **เชื่อมโยงเชิงวิเคราะห์** — your own inference from named facts (e.g. "both rely on the same foundry, so a shortage would hit both") — explain the inference in one clause, don't just assert it.
   This is a lightweight version of a full evidence ledger — one tag per claim, not a separate JSON/table file. Skip the tag only for numbers pulled directly via yfinance, which are self-evidently primary.

## Header stat strip

The stat row under the title (current price, market cap, forward P/E, upside) must also carry the headline EPS number, so a reader gets the earnings picture at a glance without scrolling to section 1:
- **Preview mode:** add a stat for consensus EPS, labeled with the fiscal quarter and "ยังไม่ประกาศ" (not yet reported) — e.g. "$0.60 · EPS ที่ตลาดคาด (Q3 FY27, ยังไม่ประกาศ)".
- **Review mode:** add a stat showing actual vs. consensus EPS together with a beat/miss tag, e.g. "$0.62 vs $0.45 · BEAT +38.7%" labeled "EPS จริง vs คาด (Q2 FY27)" — reuse the same `.tag.beat`/`.tag.miss` component used in the section 2 table so the color/word convention stays consistent across the page.

**The review-mode EPS stat cell needs to wrap, not truncate.** The header stat strip's other four cells hold short single-value text ("$56.03", "12.2x") and are fine with `white-space:nowrap` + `overflow:hidden` + `text-overflow:ellipsis`. The review-mode EPS cell holds a longer composite string ("$0.97 vs $0.93 · BEAT +4.05%") that reliably overflows that same nowrap/ellipsis rule at the stat tile's width, silently clipping the tail (the beat/miss tag and % can disappear entirely, with no visual ellipsis warning because the tile's `overflow:hidden` just hard-clips). Give this cell's class (e.g. `.eps-stat`) its own rule that overrides the inherited nowrap: `white-space:normal;overflow:visible;text-overflow:clip;line-height:1.35` (or similar) so it wraps to two lines instead of losing content. Check this in preview mode too if the consensus-EPS stat string ever grows long enough to risk the same clipping.

## Ecosystem diagram (section 0)

Don't render the ecosystem map as flat static cards in three columns — build it as an actual node-and-edge diagram so the reader can see the shape of the relationships (who feeds whom, who competes with whom), not just a list. Structure:

- **One `<svg viewBox="0 0 W H" width="100%">`, same responsive pattern as every other chart in this skill — not a fixed-pixel `position:relative` div with `overflow-x:auto`.** An early version of this component used a fixed 920px-wide absolutely-positioned container; on the artifact's ~830px content column that meant the diagram only fully showed through horizontal scrolling, and the right-hand lane rendered visibly cut off in the normal view. A `viewBox`-scaled SVG has no such fixed pixel width — it scales to whatever container width it's given, exactly like the bar/line charts elsewhere in this doc, and needs no scroll affordance.
- **Nodes as `<foreignObject>` elements holding real HTML**, not `<text>`. Each `<foreignObject x="…" y="…" width="…" height="…">` wraps a `<div xmlns="http://www.w3.org/1999/xhtml" class="eco-node2">` containing a bold title line and a muted monospace subtitle line carrying the ticker and the one-line fact that justifies the edge (e.g. "SNOW · รวม Falcon data กับ AI-native security"). This keeps the SVG viewBox scaling (so the diagram fits the page) while still getting normal HTML text wrapping (so labels never need manual width math) — the `xmlns` attribute on the inner `<div>` is required for the foreignObject content to render as HTML rather than being ignored.
- **Edges as plain `<path>` elements** in the same SVG (cubic bezier for anything not perfectly horizontal, a plain straight path when source and target share a y-coordinate) plus `<marker>` arrowheads. Compute each node's connection point (edge-center, e.g. a left-lane node's right-edge-center) from its own x/y/width/height, not eyeballed. Draw edges *before* the `<foreignObject>` nodes in document order so a node box always paints over the line ends behind it, not the other way around.
- **Small floating edge labels (the 2-4 word tag sitting mid-line, e.g. "Customer Award 2026") are plain SVG `<text>` with a small `<rect>` behind them for a background, not another `<foreignObject>`.** A `<foreignObject>` is worth its cost for a node box, where you genuinely need paragraph-style wrapping — but at the ~10px size a floating edge label runs, `<foreignObject>` text has rendered as an illegible blurred/blank bar in practice while the exact same size text via plain `<text>` renders crisp everywhere else in this document's charts. Reserve `<foreignObject>` for node boxes only.
- **Three lanes minimum: upstream partners/suppliers (left) → the company (center) → downstream customers (right).** Solid accent-colored edges with arrowheads for confirmed, named relationships; a dashed faint-colored edge (still with an arrowhead) for an unnamed/generic "องค์กรอื่นๆ" catch-all node — never *only* the generic node if named customers were findable (see the customer-search rule above).
- **A fourth branch for competitors**, since a reader asking "who competes with this company" is a different, equally common question from "who's in the supply chain." Position it below the company node, connect with dashed edges in the negative/rust color (no arrowhead — rivalry isn't a flow), and reuse the same tickers/growth figures already pulled for the section 5 valuation table so the diagram and the table agree.
- **A short legend** below the diagram (line style → meaning: solid accent = confirmed relationship, dashed faint = generic/unnamed, dashed negative = direct competitor) so the color grammar doesn't have to be inferred.
- Keep edge labels short (2-4 words, e.g. "Customer Award 2026") and positioned in the gap between lanes, never on top of a node box — one representative label per lane is enough if several edges share the same justification; put the full explanation in the caption below, same discipline as the other charts in this skill.
- **Check every text element's coordinates against every node box's actual x/y/width/height before finalizing the diagram — this recurred three times in a row on the same KO ecosystem diagram.** (1) A lane label (`ต้นน้ำ`/`ปลายน้ำ`) was placed at the same y as the first node in that lane started, rendering the label on top of the node box — leave ≥25-30px of clear vertical gap between a lane label's y and the top edge of the first node below it. (2) A floating edge-label's rect/text was given an x-range that extended past where the next lane's nodes began, so the label overlapped the leftmost ~50px of every node in that lane. (3) Even after narrowing the rect to fit fully inside the numeric lane gap, the label's *text* itself (e.g. "Bottler ใหญ่สุด (มูลค่า)") was simply too long to fit the ~90-100px gap at readable font size — the text overflowed past its own background rect, and because nodes are drawn after edge labels in document order, the node box downstream painted over (visibly clipped) the overflowing tail. A background rect sized to fit is not proof the text inside it fits too — check the *text's* rendered width against the gap width, not just the decorative rect's. When a short label can't be written to actually fit the gap, don't shrink the font past ~9-10px or truncate it — cut the label entirely if the same information already lives in the node's own subtitle text (as it did here: the node subtitles already said "Bottler อิสระใหญ่สุดด้านรายได้/ปริมาณ", making the floating label pure redundant clutter, not new information). When a lane has more than 2-3 stacked nodes, lay them out with a fixed vertical step (node height + a fixed gap, e.g. 35-40px) computed for the whole column at once, rather than picking each node's y ad hoc.

**Pre-publish checklist — run this for every new ticker's ecosystem diagram, not just when something looks off:**
1. List every node's `(x, y, width, height)` and every lane label's `(x, y)` in one place before writing the SVG. Confirm each lane label's y sits ≥25-30px above the top y of the first node in its column.
2. For every floating edge label, write down the numeric gap it must fit in (`right edge of the lane to its left` → `left edge of the lane to its right`). Confirm the label's background rect sits fully inside that gap — then *separately* estimate the label text's rendered width (roughly: Thai+Latin mixed text at font-size 10 runs ~6-7px/character) and confirm the text itself, not just its rect, fits inside the same gap.
3. Before adding any floating edge label, check whether the same fact is already stated in the node's own subtitle line. If yes, skip the floating label — it's redundant and is the first thing worth cutting when a gap is too narrow, rather than shrinking font size or truncating text.
4. This applies regardless of company or sector — a beverage company's bottler names, a chipmaker's foundry names, a bank's clearing-partner names are all just as likely to run long as "Bottler ใหญ่สุด (มูลค่า)" did here. Longer node titles (a full company name plus ticker) make the lane-gap width tighter, not more forgiving, so re-verify this checklist every time rather than assuming a layout that worked for one ticker will fit another's longer names.
5. **Recompute every edge's path endpoints from the actual node coordinates in *this* diagram — never reuse a previous ticker's edge-path numbers even when the general layout looks similar.** This bug hit the competitor edges specifically: the upstream/downstream edges were correctly recomputed for a new ticker's node positions, but the two dashed competitor-edge paths were left at the previous document's endpoint coordinates (e.g. `x=295`/`x=490`) while the competitor nodes themselves had been placed at different x positions (`x=335`/`x=535`, centers at 410/610) for this ticker's 2-node layout instead of the previous ticker's 3-node layout — so the lines visually ended in empty space well short of the node boxes instead of touching them. After placing (or moving) any node, re-derive that node's connection point from its own current `x/y/width/height` and update every path that terminates there — don't assume a path written for an earlier layout still points at the right place just because the overall diagram "looks similar."

## Document structure

Section 0 is the only one not part of either upstream skill's original spec — it was added because a reader needs the business explained before the numbers land on them. **In review mode, sections 1-2 report actuals instead of expectations — see the review variant below each.**

- **0 — Company overview.** What the business actually does, in plain language, grounded in a real detail (founding year, HQ, CEO, employee count). A revenue-mix chart by segment if the company reports segments. Immediately followed by the supplier/customer ecosystem map described above, each relationship tagged per the confidence levels above.
- **1 — Context & consensus.** Report date/timing, consensus revenue + EPS (both from the same source — don't mix yfinance EPS with web-search revenue), compared against management's own guidance range.
  - *Review variant:* replace with **actual vs. consensus vs. prior guidance** — three columns, not two. State the surprise in both absolute and % terms, and separate "beat guidance" from "beat consensus" since a company can hit its own guidance while missing a more optimistic Street number.
- **2 — Historical beat/miss.** Last 4 quarters: EPS est/actual/surprise, **plus the event-day stock reaction computed per the timing table above**. A bar chart of surprise % anchored to a real computed zero-baseline (not CSS margin hacks) with the baseline explicitly labeled ("0% = matched consensus") and each bar tagged beat/miss in words, not just color. **Re-derive the chart's y-domain from this company's actual surprise values every time** — a domain sized for one company's data will make another company's small, tightly-clustered surprises collapse into invisible slivers if reused as-is. Compute `min`/`max` of the 4 surprise values first, then pick a domain with headroom around them.
  - *Review variant:* the just-reported quarter becomes the 5th (rightmost) bar, visually distinguished (e.g. outlined or a different fill) from the 4 historical bars since it's the subject of the review, not backward-looking context.
- **3 — Analyst sentiment.** Recommendation distribution + price target range with computed upside.
  - *Review variant:* note any target/rating revisions dated after the release, if search turns them up — label them explicitly as post-earnings reactions, not the pre-earnings snapshot.
- **4 — Key metrics to watch.** Sector-specific: SaaS → ARR/NRR/RPO; retail → comps/traffic; industrials → backlog/book-to-bill; etc.
  - *Review variant:* report what these actually came in at, not what to watch for.
- **5 — Competitive landscape.** Growth-rate comparison bar chart (segment-level, e.g. cloud infra growth, not company-total — label which is which) + valuation table (market cap, forward P/E, PEG, revenue growth, op margin, upside) + a YTD price-return line chart overlaying the subject against its peers, computed from real daily closes, not illustrative.
- **6 — Scenario** *(preview only — in review mode, replace with "What changed" — a short before/after of the thesis: what the market got right, what surprised, and what's now the open question for next quarter).* Bull/base/bear with revenue/growth/driver bullets only. **Do not invent a stock-reaction percentage range per scenario** — if a defensible reaction range can be derived (e.g. from the historical event-return distribution computed above), source it explicitly; otherwise leave it out.
- **7 — Catalyst checklist.** 3-5 items, each naming the metric/decision and why it moves the stock. In review mode, these become "what to watch next quarter" instead of "before this report."
- **Footer.** Sources with pull date, confidence-tag legend (ยืนยันแล้ว / มีรายงาน / เชื่อมโยงเชิงวิเคราะห์) if any tags were used, "for research/education only, not financial advice."

## Design

**Locked template — do not redesign per ticker.** As of 2026-09-09 this project uses a fixed design system, based on the KO Q2 FY26 Earnings Review (the document the user picked as their favorite), instead of running a fresh bespoke design pass for every new company. Start every new document from `design-template.html` in this same skill folder: copy its CSS block verbatim (same variable names, same class names — masthead, statrow, sec-head/sec-num, tblwrap/table, chartcard, eco-node2, scenario-grid/scen, catlist/cat, revision-row, pt-legend, zoom-overlay, both light/dark theme blocks) and only replace the content inside `.wrap` and the per-ticker numbers. Do not invent a new palette, font pairing, or component skeleton for a new ticker. Chart coordinates still get recomputed fresh from that ticker's own real pulled data every time (never copy a previous ticker's coordinates) — only the visual system is fixed, not the data.

Publish as an Artifact. If a genuinely new component type is needed that the template doesn't cover, design it in the same visual language (same border-radius scale, same shadow token, same font roles) rather than reaching for a different look.

If Artifact publishing genuinely isn't available in the current context, fall back to a self-contained local HTML file or Markdown report rather than claiming a publish that didn't happen — don't silently downgrade the document's ambition, just its delivery mechanism.

**Also always write a local copy to the InvestView dashboard's Research page**, regardless of whether the Artifact publish succeeded — the two aren't alternatives, do both. If the current working directory is (or is inside) the InvestView dashboard project (a repo with a `dashboard/` Next.js app), save the exact same self-contained HTML document to `dashboard/research-briefs/<TICKER>.html` at that project's root (create the `dashboard/research-briefs/` folder if it doesn't exist yet; uppercase bare ticker only, e.g. `NVDA.html` — no exchange prefix, matching `symbolToFilename()` in `dashboard/src/features/research/data.ts`). The Research page (`dashboard/src/app/(dashboard)/research/page.tsx`) picks up any `dashboard/research-briefs/*.html` file automatically on next load — via `getResearchHtmlReports()` — and renders it in its own card with a live iframe, no restart needed. If the dashboard project isn't the current project (or can't be found nearby), skip this step silently rather than asking where to save it.

## Every chart is click-to-zoom

Give every `<svg>` chart in the document (surprise bars, price-target range, growth comparison, YTD line, the ecosystem diagram — all of them) a click-to-enlarge lightbox: `cursor:zoom-in` on the svg, `onclick="openZoom('<svgId>')"`, and one shared overlay near the end of the body (`.zoom-overlay` fixed, dark backdrop, centered `.zoom-overlay-inner` card with a close button) whose `openZoom(id)` clones the target svg's node into `#zoomTarget` and toggles the overlay open; close on the ✕ button, on backdrop click, and on Escape. This is a plain `<script>` with vanilla DOM calls — no runtime capability needs to be declared for it. Mention it once, briefly, near the top of the document (e.g. in the subtitle) so it's discoverable rather than left for the reader to guess at.

**Give `.zoom-overlay-inner` an explicit `width`, not just `max-width`.** `#zoomTarget svg{width:100%}` needs something concrete to resolve that percentage against. `.zoom-overlay-inner` is a flex child centered inside `.zoom-overlay` with only `max-width:min(1100px,92vw)` and no `width` — a block box in that position sizes to its content, so the cloned SVG's `width:100%` has nothing definite to resolve against and several browsers fall back to the SVG's tiny intrinsic size instead of enlarging it, which defeats the entire point of the zoom (the "zoomed" chart renders smaller than the inline one). Set `.zoom-overlay-inner{width:min(1100px,92vw)}` (width, not max-width) and `#zoomTarget{width:100%}` so the percentage chain has a real value to resolve against at every step.

## SVG chart hygiene (avoid a repeat of the ADBE mislabel bug)

When building the surprise-chart or any other hand-coded SVG for a new ticker, this exact bug recurred: a long inline `<text>` label was placed directly on the zero-baseline, and it visually collided with the first bar because its position wasn't checked against the actual bar geometry for *that* company's domain. To avoid re-hitting this:
- Keep any `<text>` sitting on or near a data mark (the zero line, an axis) short — a phrase like "0% = ตรงตามคาด", not a full sentence. Put the fuller explanation (why this domain, what it means) in an HTML `<p>` caption below the chart, never as SVG text competing for the same space as bars.
- After computing bar/line coordinates for a new ticker, sanity-check by eye (or by comparing numbers) that no label's estimated text width would overlap the nearest bar/line at that scale.
- Never copy a previous ticker's hardcoded SVG coordinates (polyline points, rect y/height, axis label positions) into a new company's chart without recomputing them from that company's own pulled numbers — this applies to the surprise chart, the YTD line chart, and the growth-rate bars alike.
- **Leave room in the `viewBox` for end-of-line labels.** On the YTD peer-comparison line chart, the per-ticker % labels sit to the right of the last data point (e.g. `x="736"` when the plotted lines end at `x="730"`). If the `viewBox` width stops at the same edge the lines end at (e.g. `0 0 760 220` with lines ending at x=730), the label text renders past the right edge of the canvas and gets silently clipped — the ticker name may show but the % gets cut off, which defeats the point of the label. Size the `viewBox` width with ~120–150px of margin beyond where the lines end (e.g. `0 0 880 220` for lines ending at x=730) so the longest label (ticker + sign + up to 3 digits + a decimal + `%`) fits inside the canvas. Check this every time — a label that fit for a 2-character ticker at +5% won't fit for a 4-character ticker at -38.3%.
- **Check for label collisions when multiple lines end close together.** When two peers' YTD returns land within ~15px of each other at the right edge, their end labels will overlap. Nudge them apart symmetrically (push the higher one up, the lower one down) until there's at least ~14px of vertical gap, rather than leaving them to collide — this happens often since peers in the same sector tend to trend together.
- **Never put `rx` (rounded corners) on a bar that sits on a shared 0% baseline** (the surprise-% chart, the growth-comparison chart, any baseline-anchored bar chart in this doc). Rounding is applied to all four corners of an SVG `<rect>` — there's no per-corner control on a plain rect — so the bottom-left/bottom-right corners round too, and where several bars of different heights meet the same baseline line, the notch reads as an uneven, "crooked" bottom edge across the chart. Use plain `<rect>` with no `rx` for these bars (flat corners, flush to the baseline); keep `rx` only on chart types where the bar doesn't sit on a shared axis line. Don't try to fix this by extending the bar past the baseline and re-drawing the axis line on top — that was tried once and instead cut a visible line straight through the bar fill, because the redrawn line's y-position no longer matched the bar's new (extended) bottom edge. Flat corners is the whole fix; nothing else needs to change.

## Price-target range component: don't float-position current/mean/median

The analyst price-target bar (low—current—mean—median—high) breaks when two of those values land close together, which happens whenever a stock's current price is near its mean target (a common, not edge, case). Floating labels positioned by percentage-left will visually collide when their percentages are within a few points of each other. Build it collision-proof from the start: only `low` and `high` get labels floated on the bar itself (their positions are fixed at 0%/100%, so they never collide with anything); `current`, `mean`, and `median` get tick marks on the bar (color-coded) but their values are written out in a plain flexbox legend row underneath — normal document flow, immune to how close the underlying numbers are.

## Each document must stand alone

If this skill has already been run for another ticker earlier in the same session, do not let that company leak into this one's prose. This happened concretely twice: an ADBE preview repeatedly said things like "more consistent than ORCL" and "unlike ORCL, customers are..."; later, in the same project, an MNST review said things like "ไม่ได้ให้กรอบตัวเลข...เหมือน HPE" and "ต่ำกว่า HPE (65%) และ KO (79%)" — in both cases the comparison made sense to the person who'd just watched the earlier ticker(s) get built, but is meaningless to anyone who opens the later document on its own, which is the actual use case. The second occurrence happened *despite this exact rule already being written down* — proof that "remember not to do this" isn't enough; treat it as a mandatory mechanical check, not a judgment call to make in the moment while writing prose.

**Before publishing, grep the draft for every other ticker built earlier in the session and read each hit in context.** Two different things can turn up, and they need opposite treatment:
- **Illegitimate leakage**: the other ticker appears only to draw a comparison for the reader's benefit ("higher than X's number," "unlike X, this company...", "than the previous two tickers in this document set"). Cut the comparison or rewrite the sentence to stand fully on its own — state this ticker's own number/fact without needing the other company as a reference point.
- **Legitimate appearance**: the other ticker is *substantively relevant to this company specifically* — it's a named competitor in the valuation table, a supplier/customer/equity-holder in the ecosystem map, a peer in the growth or YTD charts, or a source citation. These are fine and expected; don't strip them out. The test is: would this ticker belong in the document if it had never been built earlier in this same session? If yes (because it's a real peer/partner/competitor of the subject company), keep it. If the only reason it's there is to compare *this session's* two build artifacts to each other, cut it.

## Iterate like this project did

Expect several rounds of small, specific fixes rather than getting everything right in one pass:
- Ambiguous chart elements (an unlabeled dashed reference line, an unexplained footnote marker) get called out — fix by adding an explicit inline label, not just better hover text.
- A column header abbreviation users don't recognize gets swapped for the literal term they know (e.g. "%chg Revenue" over a vaguer Thai paraphrase).
- Numbers that turn out unsupported or decorative on reflection get removed rather than justified — an unexplained number is worse than no number.
- When the user points out two numbers disagree, resolve it against the primary source and fix every place the stale number appeared, not just the one flagged.
